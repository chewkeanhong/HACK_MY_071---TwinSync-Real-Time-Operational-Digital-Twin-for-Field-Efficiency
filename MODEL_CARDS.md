# TwinSync model cards

> **Both trained models are trained on simulated data.** No public dataset of telecom site
> failures or tower telemetry exists, so the training data is generated by scripts in
> this repository. The models, the training procedures and the validation are real; the
> ground truth is synthetic. Every number below is reproducible with the commands given,
> and nothing here should be read as evidence about real-world networks.

Regenerate everything:

```bash
python scripts/fetch_ndvi.py --data data
python scripts/train_edge_model.py --out models/
python scripts/train_risk_model.py --out models/
python scripts/bench_edge.py --iterations 5000 --fleet 15
python scripts/bench_twin.py --sites 15,45,90
```

## 1. Edge anomaly autoencoder — `edge_anomaly_fp32.onnx`

**Purpose.** The confirmation stage of the on-tower detector
([edge/detector.py](edge/detector.py)). Runs on a duty cycle behind two cheap
statistical tests and catches multivariate structure they miss.

| | |
|---|---|
| Architecture | Dense autoencoder, `6-16-8-16-6`, tanh (~700 parameters) |
| Framework | scikit-learn `MLPRegressor`, exported via `skl2onnx`, served by onnxruntime |
| Input | The 6 EWMA **z-scores** the detector already computes — not raw metrics |
| Output | Reconstruction MSE; above threshold `0.001123` counts as anomalous |
| Artifact | 3.0 KB on disk |
| Training data | 133,800 rows of simulated *healthy* telemetry, 15 sites |
| Validation | 5 held-out sites, never seen in training |

**Why z-scores as input.** A z-score is "how unusual is this for *this* site", so the
network is tower-agnostic: one model serves the whole fleet, a new site needs only a
warmup rather than a retrain, and there are no per-tower normalisation constants to ship
or get out of sync between training and serving.

**Why an autoencoder rather than a classifier.** It is trained only on healthy
operation, so it flags whatever it cannot reconstruct. That generalises to failure modes
absent from the training set — which, given the training set is synthetic, is the
property that matters most.

### Results

Held-out healthy false-positive rate **0.50 %** at the p99.5 threshold. Against the four
fault profiles, none of which appear in training:

| profile | median reconstruction error | flagged |
|---|---|---|
| amplifier_degradation | 5,722 | 100 % |
| power_failure | 774,938 | 100 % |
| backhaul_congestion | 14,393 | 100 % |
| antenna_misalignment | 2,244 | 100 % |

### INT8 quantisation was tried and rejected

The plan was to ship a quantised model. Measurement said not to:

| artifact | size | max drift vs FP32 | healthy false positives |
|---|---|---|---|
| **fp32 (shipped)** | 3.0 KB | 0.000002 | 0.45 % |
| int8 | 4.8 KB | 0.119 | **50.9 %** |

Two independent failures, both consequences of the model being ~700 parameters. The
Quantize/Dequantize nodes cost more bytes than the weights they save, so INT8 is
*larger*. And quantisation noise (0.119) is two orders of magnitude above the decision
threshold (0.001123), so the quantised graph flags half of all healthy traffic. FP32 was
already 3 KB; there was nothing to save. Both artifacts are committed so the comparison
can be re-run.

### Limitations

- Trained on synthetic telemetry from [edge/telemetry.py](edge/telemetry.py); the noise
  model is Gaussian with a sinusoidal diurnal term, which is tidier than reality.
- The four fault profiles are so far outside the healthy manifold that the cheap
  statistical gate catches them unaided. On this scenario the autoencoder is
  corroboration, not the thing that trips first. Its value is robustness to failure
  modes the fixed thresholds were not designed around, and that value is **argued, not
  demonstrated** by these numbers.
- No drift detection or retraining trigger.

## 2. Seven-day failure risk — `risk_lgbm.txt`

**Purpose.** Advisory risk context on the incident panel ([twinsync/risk.py](twinsync/risk.py)).

> **This model never dispatches anything.** [twinsync/priority.py](twinsync/priority.py)
> remains the deterministic, auditable dispatcher. The risk score is shown to a human,
> which is the honest place for a model trained on synthetic labels.

| | |
|---|---|
| Framework | LightGBM binary classifier, 33 boosting rounds (early-stopped) |
| Features | 14 — see [twinsync/risk.py](twinsync/risk.py) `FEATURE_NAMES` |
| Target | Failure within a 7-day horizon |
| Training data | 50,000 site-weeks across 2,500 synthetic sites |
| Validation | **Grouped by site**, 75/25. Weeks from one site share its age, feeder condition and terrain, so a random row split would leak. |
| Artifact | 114 KB |

### The hazard model

Labels come from an explicit proportional-hazards model, documented term by term in
[scripts/train_risk_model.py](scripts/train_risk_model.py). Each term cites the
reliability physics it comes from: Arrhenius thermal ageing, Coffin-Manson cycling
fatigue, increasing-hazard Weibull wear, saturating deferred-maintenance penalty, VSWR
trend as a leading indicator, height- and elevation-scaled lightning attachment,
age-gated moisture ingress, terrain exposure, and vegetation contact. Site attributes
are generated **correlated** (old sites are also overdue) so the learning problem is not
artificially easy.

### Results

| metric | model | Bayes ceiling |
|---|---|---|
| ROC-AUC | 0.6736 | 0.6872 |
| PR-AUC | 0.0546 | 0.0639 |
| Brier | 0.022299 | — |

Base rate 2.31 %. Worst calibration gap across deciles: 0.009.

**On the AUC.** 0.674 looks weak until you notice the ceiling. Failure is a Bernoulli
draw at ~2 % per week, so even a model that recovered the hazard function exactly could
not score above ~0.687 — the rest of the variance is the coin, not the model. Against
that ceiling this captures **93 % of the achievable lift above chance**. The ceiling is
computed from the generator's own probabilities, which training never sees. Quoting
0.674 without the ceiling would invite a fair objection; quoting the ceiling without
saying it comes from a synthetic generator would be worse.

### Bands are fleet-relative, and that is deliberate

The model emits a calibrated probability, which for a healthy fleet is a few percent. A
fixed cutoff would mark every site "low" for ever and the dashboard colour would carry
no information. So cutoffs are quantiles of the model's own held-out predictions —
**high = top decile (≥ 4.0 %), medium = top third (≥ 2.2 %)** — stored in
`risk_meta.json` and refitted on every training run. A site reading "4.2 % (high)" says
both things at once: the absolute risk is small, and it is still among the worst on the
network this week.

### Explainability

Attributions are exact TreeSHAP from `Booster.predict(pred_contrib=True)`, computed
per-incident at serving time, not a global importance ranking. `models/risk_shap_summary.png`
and `models/risk_feature_importance.png` are regenerated on each run. Strongest drivers
by mean |SHAP|:

| feature | mean abs SHAP |
|---|---|
| asset_age_years | 0.218 |
| peak_temperature_c | 0.182 |
| vswr_trend_30d | 0.115 |
| rainfall_intensity_mm_hr | 0.057 |
| days_since_maintenance | 0.057 |

### Limitations

- **The labels are invented.** The metrics measure how well LightGBM recovers *this
  hazard function*, not how well it predicts real failures.
- `asset_age_years`, `days_since_maintenance` and `load_factor` are derived
  deterministically from a hash of the site id, because this prototype has no asset
  register. They are the weakest inputs in the feature set.
- Trained on a synthetic distribution of 2,500 sites; the live demo scores 15 real KL
  sites whose feature distribution is narrower than training.
- **`encroachment_risk` is now served well outside its training range.** Training draws
  it from `beta(2, 3)` (mean 0.4), which is a reasonable spread for a national network.
  The real Sentinel-2 observation over this CBD gives a mean of **0.10**, so every live
  site sits in the bottom decile of what the model saw. The feature is weak enough that
  this moves scores by ~0.02 points on a 0-100 scale, but it is a genuine train/serve
  skew and the fix is to train on the distribution you will actually serve.
- No temporal validation — sites are split, weeks are not held out forward in time.

## 3. Building height imputation — `scripts/impute_heights.py`

Predates this work and is the one model here trained on **real** labels: OSM `height`
tags from 14,762 buildings in a wider AOI, used to fill in 1,712 of the 2,074 CBD
footprints that lack one. RandomForest over footprint shape plus KD-tree neighbourhood
features. Cross-validated with a leakage-aware repeated 5-fold. The artifact is the
mutated GeoJSON rather than a pickle, so re-running retrains from scratch.

## 4. Vegetation encroachment -- `data/ndvi.json`

**Purpose.** A per-site measure of how much vegetation is pressing on the compound, the
feeder run and the guy-wire anchors. Feeds the risk model as `encroachment_risk`.

This was the last invented input in the pipeline. It is now an observation.

| | |
|---|---|
| Source | Sentinel-2 L2A, Element84 `earth-search` STAC on AWS (no credentials) |
| Scene | `S2B_47NRD_20240323_0_L2A`, 2024-03-23, 4.7 % scene cloud |
| Bands | B04 (red) and B08 (NIR), 10 m; SCL at 20 m for masking |
| Reducer | median NDVI over a 120 m radius per site (~450 pixels) |
| Masking | SCL classes 0, 1, 3, 8, 9, 10, 11 rejected; a site must be >= 50 % clear |
| Artifact | `data/ndvi.json`, regenerate with `python scripts/fetch_ndvi.py` |

**Two details that change the numbers.** Processing baseline 04.00 products carry a
BOA_ADD_OFFSET of -1000; NDVI is a ratio so the 1/10000 gain cancels, but the offset does
not, and ignoring it biases NDVI toward zero over dark urban pixels. The offset actually
applied is read off the STAC item rather than assumed. Separately, the AOI straddles two
MGRS tiles, so the least-cloudy scene is not necessarily one that *contains* every site;
candidates are tried in cloud order and rejected unless every tower lands on valid,
unclouded pixels.

**NDVI to risk** is a linear stretch, `clip((ndvi - 0.10) / 0.60, 0, 1)`, not anything
learned. It is an assumption and it is echoed into the output file so a reader can
substitute their own.

### Results

Median NDVI **0.109** across the fifteen sites, range 0.046 to 0.346, every site 100 %
clear. That is a dense-urban signature, and it is the finding: the hashed stand-in this
replaced had a mean encroachment pressure of **0.59** against a measured **0.10**. A
plausible-looking guess had no way to know the KL CBD has almost no vegetation near its
rooftop sites.

**Fallback.** `python scripts/fetch_ndvi.py --synthetic` reproduces the old hashed value
exactly, and stamps `source: "simulated"` through the output so it cannot be mistaken for
an observation. `twinsync/encroachment.py` does the same in-process if no bake exists.

## 5. What is *not* a model

Stated here because these appear in the architecture diagram and could be mistaken for
learned components:

- **ST-DBSCAN** ([twinsync/stdbscan.py](twinsync/stdbscan.py)) is an algorithm, not a
  trained model. Nothing is fitted, there is no artifact, and its parameters
  (`eps_spatial`, `eps_temporal`, `min_pts`) are set from fleet geometry.
- **3D coverage** ([twinsync/coverage.py](twinsync/coverage.py)) is deterministic
  ray-casting with a Fresnel clearance criterion.
- **Vegetation encroachment** is no longer a stand-in -- see section 5. It is a real
  Sentinel-2 observation, but it is not a *model*: it is a band ratio and a linear
  stretch, both stated in `scripts/fetch_ndvi.py`.
